# AssetRail 协议与信任边界

AssetRail 是针对固定小规模参与方的有界 Optimistic 应用 Rollup。它将支付和 RWA 交割在链外执行，将充值、数据、挑战裁决和资产退出放在 L1。RWA 权属与兑付仍由发行体系提供，不能从状态根推导出链外资产真实性。

## 状态与数据

状态是 `uint64[8] cash`、`uint64[8] rwa`、`uint64[8] nonce` 三个数组。L1 root 为 `keccak256(abi.encode(state))`，即 24 个 32 字节 ABI word；每个 word 高 24 字节为零。账户下标与合约构造时的 Ethereum 地址列表绑定，无动态注册。未使用的数组位置始终为零。

操作固定 173 字节，大端整数，无动态字段：

| 字节偏移（含首不含尾） | 内容 |
| --- | --- |
| 0–1 / 1–2 / 2–3 | kind / from / to，分别 1 字节 |
| 3–11 / 11–19 | amount / price |
| 19–27 / 27–35 / 35–43 | nonce / counterNonce / sequence |
| 43–108 / 108–173 | 发送者 / DvP 对手方签名，各 65 字节 |

摘要为 `keccak256("assetrail/payment/v1" || uint256(L1ChainId) || address(contract) || payload[0:43])`。chain ID 编码为 32 字节，合约为 20 字节。签名为 secp256k1 `r || s || v`，要求低 s、v 为 27 或 28，禁止可塑性形式。非 DvP 的 price、counterNonce、副签名必须全部为零。签名绑定批次序号，因此批次重新排序或延后可能要求用户重新签署；没有跨批次有效订单池。

每批先按 L1 连续队列纳入最多 32 笔充值，再执行最多 32 笔操作。数量、余额和 nonce 均为 uint64，溢出、下溢、错误签名、重放或任一无效操作都会使全批次无效。DvP 同时变更双方两种资产余额和 nonce。提款扣减 L2 余额，随后通过已结算批次的固定操作索引领取 L1 托管资产。

合约保存完整批次 bytes，同时发布事件；充值详情也保存在 L1。观察者无需信任提交者数据库即可恢复账本。首版使用 calldata 和 storage，不使用 blob；因此**没有声称当前版本比 L1 直接转账便宜**。

## 争议与最终性

提交者无需账户准入资格，但必须支付固定保证金。只有一批可以待结算，父根固定为最近已结算状态。合约提交阶段检查长度、索引和充值范围，不执行全部签名与资产逻辑。

任何人可以在截止时间之前提供完整父状态。合约先核对父状态哈希，然后独立重执行批次：执行失败，或结果根与提议不一致，均拒绝批次并奖励挑战者保证金。父状态固定为 768 字节，执行受批次上限约束；这是一次完整重执行的争议验证，尚非适合大量账户的交互式单步证明。

`evaluate` 的确定性 require / 算术 panic 带非空错误数据；空返回的执行失败（例如子调用耗尽 gas）不能作为欺诈证据，否则攻击者可能故意压低 gas 来拒绝有效批次。测试覆盖该边界，以及最大批次、无效签名、跨域重放和错误见证。

截止前有效挑战清除 pending，不改变最终根、充值游标和批次序号。截止后任何人可 finalize，无需原提交者在线；最终根与游标原子更新。保证金采取 pull payment，奖励或退款接收方无法阻塞批次处理。签名中的 sequence 与递增 batch ID 是不同概念：被拒绝的 batch ID 不复用，但 sequence 未推进。

安全要求至少一位诚实观察者获取 L1 数据、成功执行并在挑战期内上链。若无人挑战，无效根也会被 finalize，可能导致托管资产损失；保证金大小不能替代观察者。合约的 finalize 与底层 L1 区块最终性也是两个不同阶段。完整业务最终确认应同时满足两者。

## 停止结算、审查和拒绝服务

从 lastFinalizedAt 起经过 exitDelay 后，任何人可永久冻结最后已结算根。待结算批次不能延后计时。冻结后不能新充值、出批或 finalize；参与人退出冻结余额，未消费充值退回原付款人。已结算提款与保证金仍可领取。

单批待结算设计会限制吞吐量；恶意提交者可用保证金争抢提交机会或拖延进展。全局退出保证停止结算时存在恢复通道，不提供持续出批时的逐用户强制包含。连续充值可能因目标账户 uint64 溢出而阻塞队列；当前按失败处理并可走停止结算退出，尚未实现跳过或容量预留。这些是下一阶段的可用性改进项。

## 资产与权限

结算合约没有升级管理员；参与地址和代币地址部署后固定。示例 MockAsset 只有发行者可 mint/admit，RWA 转账检查静态地址准入。它没有身份验证、投资者资格、辖区规则、动态撤销、冻结、收益分配或法定赎回。

托管仅接受 transferFrom 返回 bool 且到账金额准确的代币。充值差额检查拒绝转账税，但不构成对任意恶意 ERC-20、rebase、可升级发行方或冻结行为的适配。资金安全仍依赖接入资产合约。当前只验证仓库内两种测试代币。

旧 SettleLab BFT 的 3/4 投票不参与新 L1 合约裁决；没有把旧链简单改名为 Rollup。旧余额也没有自动变成 L1 托管负债。将来若接入 BFT 排序器，它只提供提议协调或预确认，不能绕过 L1 争议窗口。

## 已有验证与后续要求

`make assetrail-test` 检查 Go 执行与 CLI、Solidity 合约正反例和模糊性质；`make assetrail-demo` 在真实本地 EVM 运行签名、状态编码差分、充值、交割、欺诈挑战、提款、孤块恢复及退出。`make check` 覆盖所有 Go 模块。

这些结果证明本地协议闭环可运行，不证明外部审计、任意代币兼容、经济安全参数、生产容量或真实市场需求。下一阶段先实现持久化观察与挑战服务、强制包含、公开测试网故障验收，再评估状态树扩容和合规资产接入。

背景资料：[Ethereum Optimistic Rollups](https://ethereum.org/en/developers/docs/scaling/optimistic-rollups/)；[ERC-3643 标准](https://eips.ethereum.org/EIPS/eip-3643)。AssetRail 当前不宣称实现 ERC-3643。
