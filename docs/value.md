# SettleLab 的价值、证据与边界

本项目当前可证明的价值是：**实现了一个可独立检查交易授权和收录证据、可复现同步与故障恢复行为的 Go 协议实验平台。** 它适合作为协议研发能力的展示、验证方案的参考实现和四验证者 BFT 故障实验平台。商业需求尚未通过真实用户或试点验证。

## 一个具体场景

付款方发起转账，收款方需要保存记录，审计方稍后检查“谁授权了这笔交易，它是否包含在我认可的区块中”。审计方持有通过既有可信渠道获得的区块哈希，不必依赖截图，也不必让出具证据的服务一直在线。

SettleLab 为这个场景提供：

1. 钱包在本地签名，节点验证授权与 nonce。
2. authority 模式传播到指定出块节点；BFT 模式由固定四验证者独立执行、投票，三票证书才能提交。
3. 收款方导出签名交易、区块头与 Merkle 路径组成的证据包。
4. 审计方用事先认可的区块哈希离线验证证据。签名、金额、收款方或路径被修改时校验失败。

这个场景是产品假设，不是已经获得客户验证的痛点。证据包不证明余额、整块执行正确性或 BFT finality；可信区块哈希也不能由不可信证据包自行提供。

## 已实际运行的证据

2026-09-13 实测报告（本地生成报告）包含源码和二进制指纹、逐交易时序、区块检查点、测试输出及反例文件。

| 能力 | 本轮实际证据 | 能支持的结论 |
| --- | --- | --- |
| 多节点处理 | 单机四进程，64/64 笔交易确认，余额、nonce、区块哈希和状态根一致 | 固定 authority 模式下，副本能执行并收敛 |
| 确认时延 | P50 1,144.9 ms，P95 1,175.9 ms；1s 出块检查、200ms P2P 周期 | 本轮小负载的观察时延，不是生产 SLO |
| 便携审计 | 1,349 字节证据包，对应 64 笔交易区块 36,671 字节，减少 96.3% | 可以携带单笔证明，省去为该验证任务提供完整区块 |
| 离线验证 | 关闭全部节点后验真成功，CLI 含启动耗时 42.1 ms | 验证过程不需要连接原服务 |
| 防篡改与重放 | 修改签名交易金额、修改证据包、提供错误锚及重放已确认交易均被拒绝 | 测试覆盖的授权、包含关系与 nonce 检查有效 |
| 追块恢复 | 同步节点漏掉 5 块后重启，351.6 ms 追上相同状态 | 本轮跨两个同步批次的重启追块可用 |
| 单点故障边界 | authority 停机期间不确认，重启至全网一致 4,306.4 ms | 能恢复，但没有自动故障转移 |

所有节点位于同一台 macOS arm64 机器，使用临时数据目录和真实 fsync。64 笔来自一个账户，金额为 1，GasPrice=0。测量包括轮询观察误差，没有持续压测、跨机网络、数据库性能对照或真实资产。完整口径以原始报告为准。

新增的 `make smoke-bft`（已运行报告（本地生成报告））使用真实四进程和 SIGKILL，验证当前提议者停止后由其他三人自动换轮确认、只剩两人时不误确认、恢复法定人数后继续交易。这补上了旧 authority 模式暴露的单点故障能力缺口。详细实现与重跑方式见 [共识网络说明](consensus.md)；它仍不证明商业需求或生产性能。

## 为什么不能只说“数据库做不了”

| 方案 | 适合什么前提 | 与本项目的关系 |
| --- | --- | --- |
| 普通数据库与应用服务 | 各方接受统一运营方和查询权限模型 | 可满足大量记账需求；本项目没有证明能替代它或性能更好 |
| 签名日志、可信检查点与 Merkle 证明 | 重点是授权记录和离线收录验证 | 也能实现本轮核心审计价值，未必需要一条完整链 |
| SettleLab authority 模式 | 希望研究确定性执行、跨节点复制、持久化和证明接口 | 工程研究与教学收益明确，但仍信任唯一 authority |
| SettleLab 实验 BFT 模式 | 研究多方签名、三票确认和故障换轮 | 已实现真实网络与四进程故障测试，仍需更广的调度验证和安全审计 |

因此，当前选择“链”的理由是把多个协议问题放在一个一致、可运行、可测试的平台里；若实际业务只需要签名日志，应考虑更轻的方案。

## 面试演示方式

先给出场景与约束，再演示证据和反例，最后说明当前最重要的不足：

```bash
make evidence
```

命令从构建、无缓存 race 测试开始，创建四个真实节点，完成负载、审计、篡改和恢复实验，输出独立运行目录。也可以直接展示已有报告与 `bundle.json`、`trusted-anchor.json`、`offline-rejections.json`。

可据实写入简历：

> 使用 Go 实现资产结算协议实验平台，包含签名交易、Nonce 队列、确定性状态执行、libp2p 传播、持久化重放和固定出块节点同步；提供基于可信区块哈希的离线交易包含证明，使用四进程负载与故障实验验证一致性、篡改拒绝和恢复行为，并保存可复现报告。

不要写“已实现 PBFT”“支持去中心化结算”“生产级高吞吐”“已服务客户”或把本轮 53.65 tx/s 写成最大容量。若引用数据，附实验配置、日期和报告路径。

## 下一步怎样增加价值

1. **扩大 BFT 故障证据。** 自动换轮和四进程基础验收已实现；继续验证跨机分区、延迟和恶意资源消耗，并分析网络假设下的安全与恢复边界。
2. **用增长历史的负载找存储瓶颈。** 当前每次重写全历史，应先保留不同历史规模的基线，再评估增量日志或数据库，不能先宣称优化倍数。
3. **验证审计场景是否值得单独产品化。** 与潜在使用者确认其信任锚从哪里来、是否能接受签名日志、审计频率和接入成本；只有出现实际试用与可衡量改善，才能进一步证明商业价值。

本轮代码和实验完成了前述技术证据，没有把未来计划当成已实现能力。
