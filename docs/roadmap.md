# AssetRail 路线图

阶段按可重复验收推进，不以名称或代码量宣称生产就绪。

## 已实现：本地 RWA 支付 L2 闭环

- Go 多资产确定性执行，Ethereum 签名域和 Solidity 相同编码。
- 支付、RWA 转移、双签 DvP、提款和 nonce 重放保护。
- L1 托管充值、批次完整数据、带保证金提议、有界重执行挑战、窗口后结算。
- 独立 L1 重放、错误根识别、挑战 calldata、L1 重组后重新构建。
- 停止结算后的冻结退出与未消费充值退款。

验收命令：`make assetrail-test`、`make assetrail-demo`。模型限制为 8 个静态账户、2 种测试资产、每批最多 32 笔操作和 32 笔充值。详见 [协议边界](assetrail-protocol.md)。

## 下一阶段：持续运行与故障恢复

- 持久化批次提交服务、交易队列、nonce 预留与 API。
- 持续观察及自动挑战服务，密钥隔离、交易替换、L1 最终性和重组恢复。
- 强制包含或单用户强制退出；充值容量限制，避免溢出阻塞队列。
- 公共测试网部署，在多个独立运营者下验证故障与挑战窗口配置。

验收目标：提交者停止、观察者重启、RPC 延迟或重组后仍能完成正确结算或用户退出；不得把一次性脚本等同于已部署服务。

## 后续阶段：资产业务接入

- 明确发行人、托管人、实际资产权利与赎回流程。
- 适配身份准入、冻结与撤销传播，以及失败退款策略。
- 建立支付订单、结算对账、审计导出和运营界面。
- 对接一个真实业务沙箱，以交割失败率、对账成本和结算时间验证价值。

## 扩容与安全

在小规模业务验收后，评估 Merkle 状态树、账户扩展、EIP-712 钱包签名、批次流水线与 DA 成本。分别测量执行延迟、L1 最终结算时间、吞吐量与 gas，不把快速预确认写成最终到账。引入真实资金前需要独立安全审计、经济参数评估与运维演练。

原链的历史演进见 [SettleLab 路线图存档](legacy-roadmap.md)。BFT 模块继续保留回归，但不是新 L2 的结算安全依据。
